## 诚实说明

- 演示数据：故障全部由 `demo_service` 注入（日志、指标、状态均为演示值）；手册是 7 篇示例运维手册（35 chunk），检索是本地 BM25 + TF-IDF + RRF + 本地词法 Rerank（ES / Milvus 未接，cross-encoder 未装）；诊断是关键词规则推理，不是 LLM。
- 场景 6–13 的处置是演示级简化：除发布回滚（rollback_release）与配置恢复（update_config）外，其余高危步骤都是重启实例——演示环境里重启会清掉注入故障，所以 verify 能看到恢复；真实系统里重启修不好慢查询、证书过期或缓存击穿，评测只证明了“诊断 → 确认 → 执行 → 验证”的闭环能跑通，不证明真实修复手段。
- 检索仍是词法匹配：慢查询场景的手册 Top 3 里仍有一条 CPU 手册（接口 / P95 / 延迟等通用词重叠），但 CPU 假设因缺 "hot loop"只到 0.67，未影响 Top 1；历史案例匹配同样是词法匹配，跨场景运行时可能引用错根因的案例（本次评测因案例隔离未出现）。
- 场景 14 去重的另外两个分支（前一事件已结束时建新事件、超过 10 分钟时建新事件）在 harness 外手工验过：已 done 的 CPU 事件后新 demo 建了新事件；把 dedup 记录时间改到 11 分钟前后再 demo 也建了新事件。harness 内只跑了主分支（待确认事件未结束时合并）。
